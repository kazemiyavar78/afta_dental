## ۱. در چه مرحله‌ای هستیم؟

| حوزه | وضعیت |
|---|---|
| کارکرد کسب‌وکار (بیمار، پذیرش، تعرفه، سازمان، کیف پول، گزارش) | تقریباً کامل |
| زیرساخت امنیتی پایه (نشست، CSRF، bcrypt، AES-GCM، HMAC، زنجیره هش لاگ، قفل IP، ساعات کاری، سقف نشست) | پیاده شده، ولی جزئیات ممیزی و رفتارها ناقص |

**جمع‌بندی:** محصول از نظر کارکردی آماده است و در **مرحله اصلاحات دور اول امنیتی** قرار دارد. تا آماده‌شدن برای ارزیابی رسمی **۸ فاز** باقی است (بخش ۴). بیشترین کار در لاگ ممیزی، تنظیمات امنیتی، احراز هویت و نشست، و مستندات است.

## ۴. نقشه راه — فازهای باقی‌مانده

**روال هر فاز:** (۱) Claude پرامپت اطلاعات‌گیری برای Cursor می‌دهد → (۲) خروجی Cursor به Claude داده می‌شود → (۳) Claude پرامپت‌های اجرایی فاز را می‌نویسد → (۴) Cursor اجرا، تست و commit می‌کند → (۵) traceability و PROJECT_CONTEXT به‌روز و برای مشاور ارسال می‌شود.

ترتیب فازها طوری چیده شده که هر فاز روی فاز قبل بنا شود (مثلاً هیچ لاگی بدون مدل رویداد درست اصلاح نشود).

### فاز ۰ — پایه کیفیت (پیش‌نیاز همه فازها)
- اعمال قوانین Cursor (فایل‌های `.cursor/rules/afta-core.mdc`، `afta-frontend.mdc`، `afta-backend.mdc`).
- راه‌اندازی CI (GitHub Actions): `go test ./...`، `go vet`، `govulncheck`، `npm test`، `npm run build`، `npm audit`.
- تشکیل `docs/afta/traceability.md`: الزام PP ↔ ایراد مشاور ↔ فایل کد ↔ تست.
- تصمیم نهایی درباره migration (یک مسیر واحد) و افزودن `LogCleanupSummaries`.
- اصلاح README.

### فاز ۱ — بازطراحی لاگ ممیزی (موارد ۱، ۲، ۴، ۵، ۶، ۷، ۸، ۱۷، ۱۸، ۲۱)
- مدل رویداد واحد: `actor_user_id`، `actor_username`، `target_user`، `event_type`، `result`، `reason`، `ip`، `user_agent`، `details` (JSON با before/after یا diff).
- یک helper مرکزی برای ثبت رویداد؛ ممنوعیت ثبت مستقیم.
- تفکیک رویدادهای «حذف نشست» از «خروج»، با کد دلیل خروج: `user_logout`، `admin_terminated`، `max_sessions`، `idle_timeout`، `security_settings_changed`، `security_code_failed`، `ip_changed`.
- API لیست با صفحه‌بندی، فیلتر هر ستون و مرتب‌سازی سمت سرور + کامپوننت مشترک `ServerDataTable` در فرانت (برای همه جدول‌ها).
- رفع فیلتر IP؛ ثبت آغاز/توقف ممیزی و خواندن لاگ؛ انتخاب رویدادهای قابل ممیزی (FAU_SEL).

### فاز ۲ — لاگ‌های سیستمی (مورد ۲۲)
- middleware ثبت همه درخواست‌ها: کاربر، زمان، route/handler، ورودی، خروجی، IP، کد و متن خطا.
- **ماسک‌کردن اجباری** رمز، توکن، کد OTP، CSRF و فیلدهای حساس قبل از ذخیره.
- محدودیت اندازه بدنه، جدول جدا، retention و HMAC؛ صفحه با همان `ServerDataTable` و مجوز جدا.

### فاز ۳ — تنظیمات امنیتی (موارد ۹–۱۳، ۱۶، ۲۴)
- schema برای هر کلید: نوع، بازه، پیش‌فرض، گروه، برچسب و توضیح فارسی؛ اعتبارسنجی در سرور (و همان schema در UI).
- گروه‌بندی: رمز عبور / ورود و قفل / نشست / ساعات کاری / لاگ / آپلود / احراز دوعاملی.
- برچسب‌ها با الگوی «الزام …» و بازه مشخص (حداقل طول ۸–۲۵).
- بعد از هر تغییر: لاگ قبل/بعد، حذف همه نشست‌ها با لاگ برای هرکدام.
- نمایش و کارکرد واقعی «حداکثر حجم جداول لاگ» + هشدار آستانه به مدیر.
- حذف هر تنظیم بی‌اثر.

### فاز ۴ — احراز هویت و نشست (موارد ۳، ۱۴، ۱۵، ۱۸، ۱۹، ۲۰)
- رفع خطای ایجاد کاربر و توضیح `UserType` در برابر `Role` در فرم.
- قفل حساب کاربر و قفل IP برای کاربر ناموجود؛ وضعیت حساب (فعال/غیرفعال/قفل).
- **احراز هویت دومرحله‌ای پیامکی** (تصمیم کارفرما ۱۴۰۵/۰۸/۱۴):
  - interface واحد `SMSSender` با متد `Send(ctx, phone, text) error` در `internal/platform/sms`.
  - پوشه `internal/platform/sms/providers/` که هر سرویس پیامک در یک فایل جدا پیاده می‌شود؛ انتخاب provider با env.
  - یک provider «خام» (`raw`): اسکلت آماده با TODO مشخص برای افزودن سرویس‌دهنده جدید، به‌علاوه provider `console` فقط برای توسعه (خارج از build تولیدی).
  - منطق OTP جدا از ارسال: کد ۵ یا ۶ رقمی با `crypto/rand`، ذخیره فقط هش، انقضای کوتاه، سقف تلاش، فاصله ارسال مجدد، یک‌بارمصرف.
  - روشن/خاموش و پارامترها (انقضا، سقف تلاش) از تنظیمات امنیتی با اعتبارسنجی؛ کلید و نام کاربری سرویس پیامک فقط در env.
  - لاگ ممیزی: ارسال، موفق، ناموفق، انقضا، قطع سرویس پیامک — بدون متن کد و با شماره ماسک‌شده.
  - شکست ارسال پیامک یعنی رد ورود (حالت امن)، هرگز دورزدن مرحله دوم.
- خاتمه نشست با عدم فعالیت (سرور مرجع است، نه فقط تایمر UI).
- انقیاد نشست به IP و User-Agent؛ اطلاع به نشست اول؛ ورود مجدد بعد از تغییر نقش.
- نمایش آخرین ورود موفق/ناموفق بعد از ورود؛ محدودیت IP.

### فاز ۵ — داده، فایل و خروجی
- اعمال `uploadguard` روی آپلود عکس پذیرش: نوع واقعی فایل (magic bytes)، حجم، تعداد، نام تصادفی، مسیر خارج از وب‌روت.
- مجوز `reports.export` + لاگ هر خروجی + درج کاربر/زمان روی فایل خروجی.
- جایگزینی `xlsx@0.18.5`؛ فونت Vazirmatn محلی.
- رمزنگاری ستون‌های حساس بیمار (تصمیم با مشاور).
- هشدار شکست صحت داده و صفحه بررسی صحت.

### فاز ۶ — پیکربندی امن و استقرار
- TLS 1.2+ و رمزهای مجاز (IIS یا Go)، HSTS، `encrypt=true` برای SQL Server.
- حذف رمز پیش‌فرض و چاپ رمز در seed؛ خطاهای عمومی؛ حذف نسخه از هدرها.
- خارج‌کردن شبیه‌ساز کارتخوان از build تولیدی (build tag)؛ حذف مجوزهای بدون route.
- نسخه‌گذاری محصول و فرایند به‌روزرسانی با هش منتشرشده.

### فاز ۷ — مستندات ارزیابی (الزامات تضمین)
- سند هدف امنیتی (ST) شامل TSS: نحوه برآورده‌کردن هر الزام.
- مشخصات کارکردی (ADV_FSP) از روی جدول APIها.
- راهنمای کاربری برای هر نقش (AGD_OPE) و راهنمای نصب/آماده‌سازی (AGD_PRE).
- لیست پیکربندی (ALC_CMS)، گزارش آزمون، گزارش تحلیل آسیب‌پذیری (govulncheck/npm audit/اسکن).

### فاز ۸ — پیش‌آزمون داخلی
- اجرای «اقدامات ارزیابی/آزمون‌ها»ی هر الزام PP به‌صورت چک‌لیست، ثبت نتیجه، سپس تحویل به مشاور برای دور دوم.
